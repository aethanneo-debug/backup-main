7j. **An employee edit can change a record's ids** (found 2026-10-19 by the security review, pre-existing, not fixed). Reports are tied to the staff code too, so a code freed by a deletion and reused gives the new hire the predecessor's reports and attached files, unlogged (security review, 2026-11-01). `PUT /api/employees/:id` copies the request body over the record, so it can change `id` or `employeeId` with no uniqueness check. `DELETE` leaves the person's notices behind, and `POST` lets their code be reused. Since 2026-10-19, notices name the staff record's internal id, so a reused code no longer inherits them; links in other records (enrolments, reports, accounts) can still break. Personnel requests (vehicle requests filed with an advance included, 12v) store the staff code too, so a code edit hides them from the employee. Fix: drop `id` from PUT's body and refuse a duplicate `employeeId`, and a staff code equal to any record's internal id. Lookups that take the first record whose id or staff code matches confuse two people when one's code is the other's id: the participants route skipped the division check that way (fixed 2026-10-28, 12x), and a notice can still reach the wrong person (`notifyEmployee`), or a Self-Approval go unflagged (`isOwnRecord`). The TDP rule (12z) and, since 2026-10-29, enrolment (`enrollTrainingParticipants`, 12z Part B) look people up by internal id first (`employeeByKey`); the other lookups still take the first match. Since 2026-11-01 (12aa Phase 3) certificates of attendance and the employee's own seminar list match an account to its own staff record first (`accountEmployee`, `isOwnSeat`), so a staff code set to another record's internal id doesn't reach that person's certificate. Other edits still do, until this item is fixed: changing a record's internal id through `PUT`, giving someone another's staff code, or swapping two codes through a temporary one (the security review's re-check). `PUT` logs those edits only as "Changes: Contact info". Notices and emails go astray too (the security review's re-check, 2026-11-02, from verbatim copies of the code):
    - `notify` and `notifyEmployee` take the first record whose id or staff code matches the key. With B's staff code set to A's internal id, a notice keyed "emp-a" reaches whichever of the two comes first in the list.
    - `notifyEmployee` then looks the record up a second time, by its staff code. So even a notice keyed by B's own internal id, which nobody else carries, is re-keyed to "emp-a" and can land on A.
    - `sendEmployeeEmail` picks the account the same loose way, so A's email can go to B's address.
    - Switching the shared lookup to `employeeByKey` would not help: it would send B's report, request and advance notices to A in every order.
    - Each caller does know which kind of key it holds: seats store internal ids; reports, requests, advances and a group's covers store staff codes. Resolving each call by its kind of key (about 26 call sites), with one lookup, would route every notice right.
    - This item's fix makes the collision impossible instead, and leaves the lookups as they are. Live data has no collision (2026-11-02).
