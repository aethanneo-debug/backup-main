# Known Issues & Technical Debt (verified from the code — keep this list updated)

Prioritized. When you fix one, remove or update its entry here.

## 🔴 Critical — security
1. **Master/dev password backdoor.** In `/api/auth/login` and `/api/auth/change-password`, any user without `passwordHash` authenticates with `password123` **or** `sandbox-master-pass`. The seeded users in `data_store.json` have no hashes. Must be gated behind `NODE_ENV !== "production"` at minimum, ideally removed with proper seeded hashes.
2. **Hardcoded JWT secret fallbacks** — `server.ts` (`"integra-sync-secure-capstone-key"`) and `backend_fastapi/main.py` (`"superprivate_hsac_rab1_secret_9921_abc"`). Server should refuse to start in production without `JWT_SECRET`.
3. **Inconsistent server-side RBAC.** Role checks are hand-written per route; many routes rely only on `authenticateToken`. Needs a `requireRole(...roles)` middleware and an audit of all ~100 routes, plus ownership checks on `/api/employees/:employeeId/*`. ~~A concrete case (found 2026-10-08): `POST /api/activities` had no role check at all, so any signed-in user, Personnel included, could create an activity assigned to anyone with any allotted budget, then file a liquidation or reimbursement claim against it.~~ Closed 2026-10-22: the route was removed with the Activities & Assignments page (13c). ~~`GET /api/financial-transactions` answered every signed-in user, Personnel included~~: since 2026-10-22 only the Administrator, Finance and the Budget Officer (13c).
4. **PII in git.** `data_store.json`, `data_store.backup.json` are committed and contain employee records. `backend_fastapi/generated_employee_credentials.csv` is gitignored — good — keep it that way. Also (security review, 2026-10-22): attached files are stored inside `data_store.json` as base64 (item 19), and it is committed in routine `chore(data)` commits and pushed to GitHub. So the first receipt or certificate an employee attaches goes into git history for good with the next such commit. None is attached yet (0 files on 2026-10-22). Fix before real files arrive: stop committing the live file (`git rm --cached`, gitignore it, keep the example copy), then move files out of the JSON.
5. **FastAPI CORS** uses `allow_origins=["*"]` with `allow_credentials=True`.
6. **PBKDF2 at 1000 iterations** (server.ts) is far below current guidance; FastAPI uses bcrypt — the two backends hash differently, so users can't move between them without a migration.
7. JWT stored in `localStorage` (XSS-exposed). Acceptable for now; note it in any security review.
7a. **Archived accounts keep working until their token expires** (found 2026-10-08). Login refuses Archived/Deactivated accounts. But `authenticateToken` only reloads the user and never re-checks `status`, so a token issued before archiving stays valid for up to 8 hours on every route. That includes Admin-only writes such as replacing the Accountant signatory, and (since 2026-10-20) asking for a seminar's cash advance; Finance can no longer release one to an inactive payee, though. Fix: reject those statuses with 401 right after the user lookup. Not done yet: it's an auth change that needs approval.
7b. ~~`/api/dashboard/summary` sent the 8 newest audit entries, recent requests and recent transactions to every role.~~ Fixed 2026-10-08: only the Administrator receives these lists.
7c. **Account responses carry the password hash** (found 2026-10-14). `POST /api/admin/users` and `PUT /api/admin/users/:id` answer with the whole user record, `passwordHash` (salt:hash) included. Only the Administrator can call them, but the hash still reaches the browser. Fix: drop `passwordHash` from both responses.
7d. **A new account's temporary password is only emailed** (found 2026-10-14). `POST /api/admin/users` sends it by SMTP and nowhere else. With email not configured, nobody ever sees it, and the new employee can't log in. Fix: show it once to the Administrator when email isn't configured.

Both now allow HR and the Administrator, and anyone else their own records only (`canAccessEmployeeTrainingRecords`, also used by `assigned_activities`).
7f. ~~**An attached file could run a script**~~ (found and fixed 2026-10-14). A report's files were opened by setting a link's `href` to the stored content, and the server accepted any text. So a "file" sent straight to the API as a `javascript:` URL would run in the session of whoever clicked it (HR, Finance or the employee), and could send their sign-in token away (item 7). The fix:
    - The shared `downloadBase64File` (src/utils.ts) opens only base64 data URLs (`SAFE_FILE_URL`); Finance's desk and the Employee Portal use it.

    - Older stored files of another kind just won't open.
    - Since 2026-10-22 the Documents Vault uses the same check (its list's `hasFile` and its download route), and `documentProblem` tests `SAFE_FILE_URL` itself instead of a copy of the pattern, so upload and download can't drift apart.
7g. ~~**Anyone signed in could overwrite anyone's PDS**~~ (found and fixed 2026-10-14). `POST /api/employees/:employeeId/pds` had no role or ownership check, and it wrote the official position too. `GET .../pds-profile` limited only Personnel to their own, so the Finance and Budget Officers could read anyone's PDS.

7i. ~~**The dev server handed out the database to anyone on the network**~~ (found by the security review and fixed 2026-10-19; pre-existing). In development, Vite serves files from the project folder, and the server listens on `0.0.0.0`. 7j. **An employee edit can change a record's ids** (found 2026-10-19 by the security review, pre-existing, not fixed). `PUT /api/employees/:id` copies the request body over the record, so it can change `id` or `employeeId` with no uniqueness check. `DELETE` leaves the person's notices behind, and `POST` lets their code be reused. Since 2026-10-19, notices name the staff record's internal id, so a reused code no longer inherits them; links in other records (enrolments, reports, accounts) can still break. Personnel requests (vehicle requests filed with an advance included, 12v) store the staff code too, so a code edit hides them from the employee. Fix: drop `id` from PUT's body and refuse a duplicate `employeeId`, and a staff code equal to any record's internal id. Lookups that take the first record whose id or staff code matches confuse two people when one's code is the other's id: the participants route skipped the division check that way (fixed 2026-10-28, 12x), and a notice can still reach the wrong person (`notifyEmployee`), or a Self-Approval go unflagged (`isOwnRecord`). The TDP rule (12z) and, since 2026-10-29, enrolment (`enrollTrainingParticipants`, 12z Part B) look people up by internal id first (`employeeByKey`); the other lookups still take the first match.
7h. **The PDS sign-in gate can be skipped** (found 2026-10-14, pre-existing, not fixed). A user held at the gate can send just `{ "filename": "x.pdf" }` to their own `POST /pds`. That sets `pdsFieldName`, which clears the gate, without any file being uploaded or parsed. Fix: clear the gate only when a PDS is actually saved, or check the upload server-side.
7k. **Any file type can be attached, and its declared type is never checked** (found 2026-10-22 by the security review, pre-existing, not fixed). `documentProblem` accepts any MIME type inside the data URL. The portal's file inputs have no `accept` list, and the stored `type` is just what the employee's browser said.
    - Scenario: an employee attaches "Official Receipt - Hotel ….pdf.hta" declared as a PDF. Finance downloads it and opens it, and Windows runs it. Browsers warn before keeping `.hta` or `.exe`, but not `.html`, which opens as a local page (phishing).
    - Since 2026-10-22 the Documents Vault labels a file by its name's extension ("HTA file"), not the declared type.
    - Fix: allow only the kinds the office needs (e.g. PDF, JPEG, PNG). The data URL's type must match the declared type and the name's extension. Clean the name (`signatoryText`), add `accept` to both file inputs, and optionally check the first bytes (`%PDF-`, PNG, JPEG). It refuses some files employees can attach today, so the user picks the list.
7l. **A malformed request gets an HTML stack trace in development** (found 2026-10-22 by the security review, pre-existing, not fixed). There is no Express error handler. A URL with a broken escape (`/api/liquidation-submissions/%E0/documents/x`), bad JSON or a body over the limit fails before sign-in is checked, and the dev server answers with a stack trace that shows the Windows path. Production answers only "Bad Request".
    - Fix: a JSON error handler after the `/api` 404, with plain messages and 413 for "too large".
    - Also noted: an expired or invalid token gets 403, not 401. Responses carry `X-Powered-By: Express` and no `X-Content-Type-Options: nosniff`.
7m. **API answers may be kept in the browser's cache** (found 2026-10-22 by the security review, pre-existing). No `/api` answer sets `Cache-Control`, and Express adds an ETag, so JSON with employees' data (reports with their files, PDS) can stay in a shared office PC's disk cache. The Documents Vault's two routes send `no-store` since 2026-10-22. Fix: `no-store` on every `/api` answer, with one middleware.
