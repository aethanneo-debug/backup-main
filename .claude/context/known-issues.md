## 🔴 Critical — security
1. **Master/dev password backdoor.** In `/api/auth/login` and `/api/auth/change-password`, any user without `passwordHash` authenticates with `password123` **or** `sandbox-master-pass`. The seeded users in `data_store.json` have no hashes. Must be gated behind `NODE_ENV !== "production"` at minimum, ideally removed with proper seeded hashes.
    - **FastAPI's login is wider** (found 2026-11-11 by the security review of 12ag's cleanups; High, latent while the screens don't call FastAPI, Critical once it runs anywhere reachable; not fixed, since the work is Express only). `backend_fastapi/main.py` (`/api/auth/login`, the `verify_password` check) takes `password123` for **any** existing account, whatever its bcrypt hash, the Administrator's included. An unknown username with that password answers 500, which also tells which usernames exist. With item 2's public fallback secret and item 5's open CORS it is a full takeover. Fix: refuse whenever `verify_password` fails (drop the `password123` branch).
2. **Hardcoded JWT secret fallbacks** — `server.ts` (`"integra-sync-secure-capstone-key"`) and `backend_fastapi/main.py` (`"superprivate_hsac_rab1_secret_9921_abc"`). Server should refuse to start in production without `JWT_SECRET`.
3. **Inconsistent server-side RBAC.** Role checks are hand-written per route; many routes rely only on `authenticateToken`. 7j. **An employee edit can change a record's ids** (found 2026-10-19 by the security review, pre-existing, not fixed). Reports are tied to the staff code too, so a code freed by a deletion and reused gives the new hire the predecessor's reports and attached files, unlogged (security review, 2026-11-01). `PUT /api/employees/:id` copies the request body over the record, so it can change `id` or `employeeId` with no uniqueness check. `DELETE` leaves the person's notices behind, and `POST` lets their code be reused. Since 2026-10-19, notices name the staff record's internal id, so a reused code no longer inherits them; links in other records (enrolments, reports, accounts) can still break. Personnel requests (vehicle requests filed with an advance included, 12v) store the staff code too, so a code edit hides them from the employee. Fix: drop `id` from PUT's body and refuse a duplicate `employeeId`, and a staff code equal to any record's internal id. Lookups that take the first record whose id or staff code matches confuse two people when one's code is the other's id: the participants route skipped the division check that way (fixed 2026-10-28, 12x), and a notice can still reach the wrong person (`notifyEmployee`), or a Self-Approval go unflagged (`isOwnRecord`). The TDP rule (12z) and, since 2026-10-29, enrolment (`enrollTrainingParticipants`, 12z Part B) look people up by internal id first (`employeeByKey`); the other lookups still take the first match. Since 2026-11-01 (12aa Phase 3) certificates of attendance and the employee's own seminar list match an account to its own staff record first (`accountEmployee`, `isOwnSeat`), so a staff code set to another record's internal id doesn't reach that person's certificate. Other edits still do, until this item is fixed: changing a record's internal id through `PUT`, giving someone another's staff code, or swapping two codes through a temporary one (the security review's re-check). `PUT` logs those edits only as "Changes: Contact info", and so a changed hire date too, which "Hired after the TDP" quotes as its evidence (12ab, 12ad). The TDP rule also counts every need stored under either of a person's ids (`employeeCoveredNeeds`), so with B's staff code set to A's internal id, B is identified by A's needs too, though the person is looked up strictly (found by 12ad's security review, 2026-11-08). Add Training Need refuses to add a need to someone whose id another record carries (12ad); an upload or a replacement can still do it. Notices and emails go astray too (the security review's re-check, 2026-11-02, from verbatim copies of the code):
    - `notify` and `notifyEmployee` take the first record whose id or staff code matches the key. With B's staff code set to A's internal id, a notice keyed "emp-a" reaches whichever of the two comes first in the list.
    - `notifyEmployee` then looks the record up a second time, by its staff code. So even a notice keyed by B's own internal id, which nobody else carries, is re-keyed to "emp-a" and can land on A.
    - `sendEmployeeEmail` picks the account the same loose way, so A's email can go to B's address.
    - Switching the shared lookup to `employeeByKey` would not help: it would send B's report, request and advance notices to A in every order.
    - Each caller does know which kind of key it holds: seats store internal ids; reports, requests, advances and a group's covers store staff codes. Resolving each call by its kind of key (about 26 call sites), with one lookup, would route every notice right.
    - Since 2026-11-03 (12ab) a staff record leaves the training lists, and can't be paid, once every account linked to it is archived. So a staff code freed by deleting a record and reused gives the new hire the old archived account: they vanish from every training list (and couldn't be paid before either). `POST /api/admin/users` refuses such a code, but `POST /api/employees` checks staff records only. This item's fix should also refuse a staff code an account carries.
    - This item's fix makes the collision impossible instead, and leaves the lookups as they are. Live data has no collision: counted on a sandbox copy on 2026-11-03, no staff code equals another record's internal id, none is duplicated, every seat and HR record names someone, and every account has a staff record.
    - The older training routes (`/trainings`, `/assigned_activities`, `/history`) now refuse a key naming someone else's record, but still read rows by both of the record's ids. So with B's staff code set to A's internal id and B's login on that code, B reads A's rows (Phase 7's security review). This item's fix closes it. The new history route isn't affected: under such a collision it answers B with B's own rows, or 403. A code swap, or a shared code with a relinked login, does reach the other person's copy there too.
